A tiny backend for kevhub

Right now kevhub can show you things but can't save anything you do on it. This plan gives every page a one-line kevhub.save() and gives Kevin a real database on the box. No passwords, no emailing results.

Recommendation: Vercel Function + Neon Postgres

One small Vercel project (kevhub-api) with two or three endpoints, backed by a free Neon Postgres database added from the Vercel Marketplace. kevhub pages stay on GitHub Pages.

Why this one

  • Best for Kevin to work with. It's real Postgres, so Kevin can just run psql or Python with the connection string. Each record's payload is stored as jsonb, so a new mini-app is just a new app name, with no migrations and no schema to declare. JSON queries, views, and indexes all work, and the docs (Postgres, Neon, Vercel) are about as good as docs get.
  • You already have the pieces. Your Vercel account is already connected to Kevin and has 6 projects, so no new vendor. Neon is billed through Vercel, so there's no separate account or card.
  • $0 a month at your scale, with plenty of headroom: 1M function calls and 100 compute-hours a month, 1 GB of storage. If you ever want it to always stay awake, that's about $1–5 a month.
  • Nothing pauses for good. The database sleeps after 5 minutes idle and wakes in a few hundred milliseconds. Unlike Supabase's free plan, it never gets shut down for a week of inactivity, which matters when you're only on it every couple of weeks.

Runner-up: Cloudflare Workers + D1

It's the fastest (practically no cold start), free, and has a great CLI (wrangler d1 execute). It loses because it's a new account plus an API token to set up, and its SQLite JSON support is a bit weaker than Postgres jsonb. A good choice if we ever move kevhub's hosting to Cloudflare.

The primitives

1. Two tables, so new apps never need a migration

-- append-only log: swipes, ratings, feedback, form answers
create table events (
  id         bigserial primary key,
  app        text not null,          -- 'style-swipe', 'music', 'survey-x'
  kind       text,                   -- 'swipe', 'feedback', 'answer'
  key        text,                   -- item id, e.g. 'e28' or a track id
  device     text,                   -- random per-device id (see Security)
  data       jsonb not null,         -- anything; no schema
  created_at timestamptz default now()
);
create index on events (app, created_at desc);
create index on events using gin (data);

-- latest-state store: "current answers", settings, drafts
create table docs (
  app text, key text, data jsonb not null,
  updated_at timestamptz default now(),
  primary key (app, key)
);

2. Endpoints (one Vercel project)

POST /api/save    {app, kind?, key?, data}       public, write-only, rate-limited
PUT  /api/doc     {app, key, data}                public upsert into docs (allowlisted apps)
GET  /api/mine?app=style-swipe                    returns only this device's events
GET  /api/list?app=…&since=…    Authorization: Bearer $KEVHUB_ADMIN   Kevin only
GET  /api/health                                  warm-up / uptime ping

3. The page helper (/kevhub/kv.js, under 1 KB)

<script src="../kv.js"></script>
<script>
  kevhub.save('style-swipe', {id:'e28', vote:'like'}, {kind:'swipe', key:'e28'});
  const mine = await kevhub.mine('style-swipe');   // reload past answers
</script>

The helper creates a random device id once (crypto.randomUUID() in localStorage), sends it with each save, queues saves offline and retries, and uses keepalive so a swipe isn't lost if you close the tab.

4. How Kevin works with it

export DATABASE_URL=…   # stored once on the box, chmod 600, never in the repo
psql "$DATABASE_URL" -c "select data->>'vote', count(*) from events
                         where app='style-swipe' group by 1"
python3 -c "import psycopg; …"               # same thing from analysis scripts
curl -H "Authorization: Bearer $KEVHUB_ADMIN" https://kevhub-api.vercel.app/api/list?app=music

Kevin gets full SQL against the database, and the HTTP read route is a backup. A small kh wrapper on the box (kh list music, kh sql "…") makes the common queries one word.

Security without passwords

  • Writes are public but blind. Anyone with the URL could post to /save, but nobody can read through it. The worst case is junk rows, which Kevin can filter or delete.
  • Guardrails on writes: only requests from tyler-simons.github.io are accepted, payloads are capped at 16 KB, app names must match ^[a-z0-9-]{1,40}$, and each device is limited to about 60 writes a minute (a simple count in Postgres).
  • Per-device id, not a password. Your phone gets a random 122-bit id on first visit. /mine returns only that device's rows, so the id acts as a key that can't be guessed. Nothing for you to type, ever.
  • Optional "trusted device" link. If we ever want writes locked down, Kevin sends you a one-time link (…/kevhub/#k=…) that saves a secret in your browser. You tap it once per device and never see it again.
  • Kevin's reads use either the database URL or a long admin token. Both live only on the box and in Vercel environment variables, never in the repo or the pages.
  • Privacy: data lives in a private Neon database in your account, encrypted at rest. Pages are noindex. Comp and job-search info never goes in here; that stays out of kevhub entirely.

Migration plan

  1. Day 1: create the project and database, add the two tables and the endpoints, add kv.js to kevhub, and set up the kh CLI on the box. Smoke test with curl.
  2. Style Swipe: each swipe saves as it happens (app=style-swipe, kind=swipe). The "Send results to Kevin" button just becomes "Done", and your Oct 17 results get backfilled.
  3. Music picks: add 👍 / 👎 / "listened" buttons to each pick (app=music, kind=feedback). analyze.py reads them before each biweekly run instead of relying on feedback.json by hand.
  4. Shopping picks: ❤️ / skip / "bought" buttons on the style shopping page.
  5. Later: any new mini-app (ratings, quick surveys, the interview drills) just calls kevhub.save('new-app', …). No backend work needed.
  6. Optional: move kevhub hosting itself to Vercel so pages and API share one domain. That's not needed now, since GitHub Pages works fine with cross-origin requests.

Setup checklist

  1. You Say go.
  2. You In Vercel, go to Storage → Create Database → Neon, choose the Free plan, and accept the Marketplace terms. That's about 3 clicks, no card. (Vercel won't let Kevin accept the terms for you.)
  3. You Give Kevin a way to deploy: either approve a vercel login prompt on Kevin's box once, or create a Vercel token (Settings → Tokens) scoped to your account and paste it to Kevin. One time only.
  4. Kevin: create the kevhub-api project and connect it to the Neon database (which sets DATABASE_URL), then set KEVHUB_ADMIN.
  5. Kevin: create the tables, deploy the endpoints, and test them with curl from the box.
  6. Kevin: add kv.js to kevhub, wire up Style Swipe, and push.
  7. You Swipe once on your phone to confirm it works. Kevin checks that the row arrived.
  8. Kevin: wire up music feedback and the shopping picks, then update analyze.py.

Details and notes

Why not Supabase, the usual answer?

For a public page writing data, Supabase is the most common pick on Reddit and HN. You expose the anon key, turn on row-level security, and allow inserts only. It's a good product. But free projects are paused after 7 days without enough database activity. They can be restored, but kevhub use is bursty (a swipe session, then quiet for two weeks), so we'd keep hitting it. Pro costs $25 a month, over budget. Neon via Vercel gives the same Postgres ergonomics for $0.

Cold starts

Vercel's Fluid compute keeps functions warm, and Vercel reports no cold start on about 99% of requests. The real delay is Neon waking up (a few hundred milliseconds after 5 idle minutes). Saves are fire-and-forget, so you'd never notice. If it ever bugs us, we can turn off sleep on Neon's paid plan for about $1–5 a month.

Why the Vercel function, and not the database straight from the browser?

The database URL is a full-access secret, so it can never go in a page. The function is the narrow, write-only gate. Kevin skips the function and uses SQL directly.

Limits we'd have to really try to hit

  • Vercel Hobby: 1M function calls and 4 CPU-hours per rolling 30 days. If we exceed them, the feature pauses; nothing gets billed.
  • Neon Free: 100 CU-hours a month (about 400 hours awake at the smallest size), 1 GB storage, 5 GB transfer. A year of swipes and feedback is well under 10 MB.

Lock-in

Very low. It's standard Postgres (pg_dump works) plus about 100 lines of function code. Kevin can also export a nightly JSON backup into the box or a private repo.
